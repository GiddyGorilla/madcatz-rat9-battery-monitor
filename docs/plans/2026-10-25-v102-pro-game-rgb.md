# Implementation Plan: V102 Pro Game RGB Integration

## Overview

Add EWEADN V102 Pro support to the existing R.A.T. 9 tray application. The
work is delivered in four independently testable phases: battery, unified UI,
per-key RGB, and automatic game profiles.

The implementation uses the V102 receiver's official HID protocol directly and
does not depend on E HUB at runtime.

## Requirements

- Detect the V102 Pro 2.4 GHz receiver with VID `0x05AC` and PID `0x024F`.
- Read battery level and charging state using command `0x87`.
- Show the lowest connected-device battery in one tray icon.
- Record battery history and estimate runtime after enough discharge data.
- Read and apply per-key RGB for the V102 Logo matrix.
- Save named profiles locally without an EWEADN account.
- Associate one or more executable paths with each profile.
- Apply a game profile after process start and restore a base profile on exit.
- Reapply a pending profile after keyboard reconnect.
- Send no firmware, DFU, bootloader, or erase commands.
- Preserve all existing R.A.T. 9 behavior.

## Architecture Changes

- `src/DeviceModels.cs`: shared device identity, battery, connection, and RGB
  value objects.
- `src/IDeviceBatterySource.cs`: battery adapter contract.
- `src/V102Protocol.cs`: pure protocol encoding, decoding, key maps, and report
  chunking.
- `src/V102HidDevice.cs`: Windows HID discovery and transport.
- `src/V102BatterySource.cs`: V102 battery adapter and history sampling.
- `src/V102RgbEditor.cs`: per-key editor control.
- `src/KeyboardProfileStore.cs`: versioned local profile persistence.
- `src/GameProfileMonitor.cs`: process detection, priority, and restoration.
- `src/DeviceCoordinator.cs`: device polling, retries, tray icon selection, and
  event coordination.
- `src/Rat9BatteryTray.cs`: wire the coordinator, tabs, and new controls into
  the existing tray and detail window.
- `src/Rat9BatteryCore.cs`: implement the battery-source contract for R.A.T. 9.
- `src/TestHarness.cs`: deterministic tests for protocol, profiles, estimator,
  and process-priority logic.
- `build.ps1`: compile the test harness and include new sources.

## Implementation Steps

### Phase 1: V102 Battery — Minimum Viable

1. **Add shared battery models**
   (File: `src/DeviceModels.cs`)
   - Action: Add device identity, battery reading, connection state, and error
     value objects.
   - Why: Both device adapters and the UI need one stable data contract.
   - Dependencies: None.
   - Risk: Low.

2. **Implement pure V102 protocol helpers**
   (File: `src/V102Protocol.cs`)
   - Action: Encode command `0x87`, validate response command/length, and decode
     percentage and charging state.
   - Why: The risky byte-level logic must be testable without hardware.
   - Dependencies: Step 1.
   - Risk: Medium.

3. **Add Windows HID discovery**
   (File: `src/V102HidDevice.cs`)
   - Action: Enumerate HID interfaces for `1452:591`, select the `2.4G`
     dakai-hid collection, open it, and expose feature-report request/response.
   - Why: E HUB uses WebHID over standard Windows HID, so no vendor driver is
     required.
   - Dependencies: Steps 1–2.
   - Risk: High.

4. **Implement V102 battery adapter**
   (File: `src/V102BatterySource.cs`)
   - Action: Poll battery, serialize transport calls, and convert valid
     responses into shared battery readings.
   - Why: Battery availability is the first independently useful milestone.
   - Dependencies: Step 3.
   - Risk: Medium.

5. **Add a standalone V102 diagnostic**
   (File: `src/V102BatteryProbe.cs`)
   - Action: Print HID identity, model, percentage, charging state, and raw
     protocol status.
   - Why: Physical-device verification must be possible before UI changes.
   - Dependencies: Step 4.
   - Risk: Low.

6. **Add protocol and HID tests**
   (File: `src/TestHarness.cs`)
   - Action: Test valid, short, malformed, zero, and charging responses.
   - Why: Avoid reporting malformed responses as 0 percent.
   - Dependencies: Steps 2–4.
   - Risk: Low.

7. **Update the build and verify hardware**
   (File: `build.ps1`)
   - Action: Compile the adapter, probes, and test harness; run the harness and
     physical V102 battery probe.
   - Why: Phase 1 is accepted only when the real keyboard returns the same
     battery level as E HUB.
   - Dependencies: Steps 1–6.
   - Risk: Medium.

### Phase 2: Unified Device UI

1. **Adapt R.A.T. 9 to the battery-source contract**
   (File: `src/Rat9BatteryCore.cs`)
   - Action: Wrap the existing battery reader in the shared interface without
     changing its worker isolation.
   - Why: The coordinator must handle both devices consistently.
   - Dependencies: Phase 1 Step 1.
   - Risk: Medium.

2. **Add the device coordinator**
   (File: `src/DeviceCoordinator.cs`)
   - Action: Poll both adapters, merge results, select the lowest valid battery,
     and expose change events.
   - Why: One tray icon and one detail window should represent both devices.
   - Dependencies: Phase 1; Phase 2 Step 1.
   - Risk: Medium.

3. **Add V102 battery history**
   (File: `src/V102BatterySource.cs`)
   - Action: Persist timestamped discharging samples and reuse the existing
     estimator rules without a fabricated full-runtime baseline.
   - Why: V102 runtime must be learned rather than guessed.
   - Dependencies: Phase 1 Step 4.
   - Risk: Medium.

4. **Add tabbed device details**
   (File: `src/Rat9BatteryTray.cs`)
   - Action: Add Overview, R.A.T. 9, V102 Pro, RGB, Game profiles, and Settings
     tabs; preserve auto-dismiss and pinned behavior.
   - Why: New functionality must not overload the original compact panel.
   - Dependencies: Step 2.
   - Risk: Medium.

5. **Update the combined tray icon and tooltip**
   (File: `src/Rat9BatteryTray.cs`)
   - Action: Show the minimum connected battery and list both devices in the
     tooltip.
   - Why: The tray remains the glanceable primary interface.
   - Dependencies: Step 2.
   - Risk: Low.

6. **Add coordinator tests**
   (File: `src/TestHarness.cs`)
   - Action: Test both connected, one connected, disconnected, invalid battery,
     and lowest-device selection.
   - Why: Combined-state logic must remain deterministic.
   - Dependencies: Steps 1–5.
   - Risk: Low.

7. **Verify unified UI physically**
   (File: `build.ps1`)
   - Action: Build and run both physical probes, then verify tabs and tray
     tooltip with R.A.T. 9 and V102 connected.
   - Why: Phase 2 acceptance requires both devices to update independently.
   - Dependencies: Steps 1–6.
   - Risk: Medium.

### Phase 3: Per-Key RGB and Profiles

1. **Add V102 key and matrix maps**
   (File: `src/V102Protocol.cs`)
   - Action: Encode the 99 logical keys, Logo light, 20-byte matrix, and
     deterministic report chunking.
   - Why: The UI must use logical keys while the device receives protocol IDs.
   - Dependencies: Phase 1 protocol.
   - Risk: High.

2. **Add RGB read/write operations**
   (File: `src/V102HidDevice.cs`)
   - Action: Implement serialized layout read and apply operations with bounded
     timeouts and no infinite retries.
   - Why: Live per-key editing requires safe bidirectional HID transactions.
   - Dependencies: Step 1.
   - Risk: High.

3. **Add versioned profile storage**
   (File: `src/KeyboardProfileStore.cs`)
   - Action: Implement schema-v1 JSON loading, validation, atomic writes, and
     recovery from invalid profiles.
   - Why: Profiles must survive restarts without corruption.
   - Dependencies: None.
   - Risk: Medium.

4. **Build the per-key editor**
   (File: `src/V102RgbEditor.cs`)
   - Action: Render the 99-key keyboard, selection tools, color picker,
     brightness, logo light, copy/paste, undo, and reset.
   - Why: This is the requested primary RGB interaction.
   - Dependencies: Steps 1–3.
   - Risk: Medium.

5. **Add profile controls and live apply**
   (File: `src/Rat9BatteryTray.cs`)
   - Action: Add save, duplicate, rename, delete, base-profile selection, and
     explicit retry feedback.
   - Why: Custom layouts need a complete local workflow.
   - Dependencies: Steps 3–4.
   - Risk: Medium.

6. **Add protocol and persistence tests**
   (File: `src/TestHarness.cs`)
   - Action: Test every logical key mapping, chunk boundaries, JSON round trips,
     invalid profiles, and transactional failure behavior.
   - Why: RGB report errors are difficult to diagnose on hardware.
   - Dependencies: Steps 1–3.
   - Risk: Low.

7. **Verify every key physically**
   (File: `build.ps1`)
   - Action: Apply a distinct-color diagnostic layout and confirm key/logo
     mapping, brightness, restart persistence, and reconnect behavior.
   - Why: Phase 3 is accepted only with physical visual verification.
   - Dependencies: Steps 1–6.
   - Risk: High.

### Phase 4: Game Profiles and Hardening

1. **Add process-to-profile association**
   (File: `src/KeyboardProfileStore.cs`)
   - Action: Store normalized executable paths per profile and expose missing
     path validation.
   - Why: Matching process names alone is ambiguous.
   - Dependencies: Phase 3 profile schema.
   - Risk: Low.

2. **Add the game monitor**
   (File: `src/GameProfileMonitor.cs`)
   - Action: Scan processes every two seconds, apply foreground priority, emit
     activation/restoration events, and support deterministic fake inputs.
   - Why: Automatic switching must be testable separate from UI and HID.
   - Dependencies: Step 1.
   - Risk: Medium.

3. **Wire game profiles to RGB application**
   (File: `src/Rat9BatteryTray.cs`)
   - Action: Add executable picker, profile binding, one-second settle delay,
     pending reconnect application, and base restoration.
   - Why: This completes the requested game workflow.
   - Dependencies: Step 2; Phase 3 apply path.
   - Risk: High.

4. **Add startup and reconnect handling**
   (File: `src/DeviceCoordinator.cs`)
   - Action: Reassert the currently selected game profile after keyboard
     reconnect and apply it when a configured game is already running at app
     start.
   - Why: Wireless keyboards disconnect during sleep and charging.
   - Dependencies: Steps 2–3.
   - Risk: Medium.

5. **Add process-monitor tests**
   (File: `src/TestHarness.cs`)
   - Action: Test launch, exit, simultaneous games, foreground priority,
     missing paths, reconnect, and restoration.
   - Why: Profile switching must never oscillate or restore incorrectly.
   - Dependencies: Steps 1–4.
   - Risk: Low.

6. **Harden diagnostics and recovery**
   (File: `src/Rat9BatteryTray.cs`)
   - Action: Add bounded errors, no retry loops, connection guidance, and
     protocol-only diagnostics without keystroke capture.
   - Why: A keyboard control service must fail visibly and safely.
   - Dependencies: Steps 1–5.
   - Risk: Medium.

7. **Run the complete acceptance suite**
   (File: `build.ps1`)
   - Action: Run unit tests, both hardware probes, R.A.T. 9 regression checks,
     full RGB verification, and game launch/exit/reconnect scenarios.
   - Why: Phase 4 is the release gate.
   - Dependencies: All prior steps.
   - Risk: High.

## Testing Strategy

### Unit

- `src/TestHarness.cs` validates V102 battery reports, key maps, report chunks,
  profile JSON, profile validation, process priority, debounce decisions, and
  runtime-estimator behavior.

### Integration

- `src/V102BatteryProbe.cs` validates the real receiver and battery protocol.
- `src/Rat9BatteryProbe.exe` remains the R.A.T. 9 regression probe.
- A fake HID transport validates RGB apply failures without touching hardware.
- A fake process monitor validates game activation and restoration without
  launching games.

### End-to-end

1. Start with both devices connected and verify the lowest percentage appears
   in the tray.
2. Assign distinct colors to several keys and the logo, then restart and verify
   persistence.
3. Bind a test executable to a profile, launch it, and verify application
   within three seconds.
4. Disconnect and reconnect the keyboard during the test game and verify the
   profile is reapplied.
5. Close the executable and verify the base profile is restored.
6. Verify the R.A.T. 9 continues updating throughout.

## Success Criteria

- [ ] V102 battery and charging state match E HUB on the same physical device.
- [ ] R.A.T. 9 and V102 both appear in the unified tray UI.
- [ ] Every V102 key and the logo can receive an independent color.
- [ ] Saved profiles survive app restart.
- [ ] Game profiles activate and restore within the documented behavior.
- [ ] Reconnection during a game reapplies the correct profile.
- [ ] No vendor desktop software, cloud account, or kernel driver is needed for
      V102 control.
- [ ] No firmware, DFU, or erase command is reachable from normal UI code.
- [ ] All automated tests pass and physical acceptance steps are recorded.
